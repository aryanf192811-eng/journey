# Antigravity + Stitch UI build prompt — Journey Intelligence

Generated by the `antigravity-stitch-ui-prompt` skill, grounded in
`docs/UI.md`, `docs/PRD.md`, `CLAUDE.md`, and this repo's actual component
files — not a generic template. Two parts, used in order. See that skill
(`~/.claude/skills/antigravity-stitch-ui-prompt/SKILL.md`) for the
methodology and the real Stitch/Antigravity MCP mechanics this follows.

## Design reasoning (why this direction, before the prompts)

**Industry category (per UI/UX Pro Max Skill's industry-reasoning
approach):** this product handles real money (fares) and makes an explicit
promise never to fabricate confidence it doesn't have — that reads closer
to **trust-sensitive Finance** than to generic travel/lifestyle apps, blended
with **Services/Travel** for warmth (this should feel like a journey-planning
command center, not a bank statement).

**Anti-patterns to avoid, stated explicitly so a design pass can't drift
into them:**
- No "AI purple/pink gradient" — the skill's own flagged anti-pattern for
  banking-adjacent trust UIs, and this product is exactly that adjacent.
- No glassmorphism/neumorphism — decorative depth fights the actual job,
  which is fast comparative scanning of fare/time/risk across journeys.
- No fake urgency copy ("only 2 seats left!") — this is already a hard
  rule in `docs/UI.md`, not just a style preference.
- No emoji-as-icon (current `✓`/`⚠`/`✕` glyphs in `WhyThisRoute.tsx` and
  `ExpansionBanner.tsx` should become real SVG icons — Heroicons or
  Lucide).

**Information hierarchy:** on the results list, fare / duration / transfer
count / booking-viability badge / connection-risk badge must be scannable
in under 2 seconds per card — that's the whole job of that screen. The
"why this route" explanation is deliberately *not* on that screen (per
`docs/UI.md`) — it's detail-on-demand on the journey page, and must never
be collapsed or hidden there; it's this product's main trust-building
element versus ixigo/ConfirmTkt's single opaque percentage.

## PART A — Stitch design brief

Paste into stitch.withgoogle.com, "Web" project type, project name
`journey-intelligence-v1` (Part B fetches it by this name).

```
Design a 3-screen web app called "Journey Intelligence" — an Indian
multi-modal train journey planner. Positioning: a "travel command center,"
not an IRCTC clone or a generic OTA. It searches and explains journeys; it
never books anything, so there is no "Book now" button anywhere.

Style direction: clean, typographic, data-dense but calm — closer to a
trustworthy fintech dashboard than a flashy travel app. Generous spacing,
strong type hierarchy, badges/labels instead of raw percentages or naked
numbers wherever a judgment is being communicated (e.g. "High" not "87%").
Avoid purple/pink AI-gradient cliches, avoid glassmorphism/neumorphism,
avoid stock-photo travel imagery — this is a tool, not an ad. No fake
urgency language anywhere ("only 2 seats left" style copy is explicitly
forbidden). No emoji as icons — real iconography (Heroicons/Lucide style
outline icons).

Screen 1 — Search (single form, no wizard/steps):
- Origin and destination fields, each with an autocomplete dropdown
  showing station name, code, and city
- A date RANGE (earliest date, latest date) — two date pickers, not one
- Optional budget max input (₹)
- Class selection as a multi-select chip/pill group: SL, 3A, 2A, 1A, CC
- Max transfers as a 3-option segmented control: 0 / 1 / 2
- Passenger count number input
- One submit button; while loading, show exactly one calm status line
  below the button (e.g. "Searching across your date range for viable
  journeys…") — never a fake multi-step progress bar, since the search is
  a single synchronous call, not a multi-stage pipeline

Screen 2 — Results list:
- Header showing the echoed query in plain language (route, date range,
  budget)
- Below the header, an optional dismissible info banner (amber/neutral
  tone, not alarming) suggesting nearby alternate stations when the exact
  search came back thin — must look clearly secondary/optional, never
  blended into the main list
- A vertical list of journey cards. Each card:
  - route as station codes joined by arrows (e.g. "BRC → NDLS → MFP")
  - total fare (large, prominent) and total duration + transfer count
    (secondary line)
  - a "booking viability" badge with exactly 4 states: High (confident
    positive color), Medium (caution color), Low (warning color), Unknown
    (neutral grey — this is a common, expected state, not an error, and
    must never borrow a color that implies data that doesn't exist)
  - a separate "connection risk" badge (green/yellow/red) reflecting the
    worst transfer in that journey — visually distinct from the viability
    badge, they answer different questions
  - the whole card is a link to the detail screen
- An empty state (genuinely no results, not an error): calm reassuring
  copy, one suggestion to loosen a constraint, button back to search with
  values preserved

Screen 3 — Journey detail:
- Back link to results
- Full leg-by-leg itinerary: train name/number, class, from/to station and
  time, fare — presented as a timeline/vertical stepper, not a table
- Per-transfer: buffer time, the same connection-risk badge, one-line
  plain-language reason (e.g. "1h05m at NDLS — moderate platform
  distance")
- A prominent "Why this route" section: a checklist of positive reasons
  (✓-style, but as real icons) rendered as its own clearly-labeled block —
  this is the single most important trust element on the page, never
  collapse it into a summary or hide it behind a toggle
- A separate "Cautions" list (⚠-style icons) directly below or beside it,
  visually distinct (not the same color as the positive list)
- No booking CTA of any kind

All 3 screens: must work responsively from a 375px phone width up through
a 1440px desktop width without horizontal scroll or clipped text. Meaning
must never rest on color alone (pair every risk/viability badge with a
text label, not just a colored dot).
```
