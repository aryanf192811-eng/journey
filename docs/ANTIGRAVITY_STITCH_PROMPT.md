## Design reasoning (real query output, not guesswork)

Queries run via `python ".../ui-ux-pro-max/scripts/search.py" "<query>" --domain <domain>`:

- `"travel search comparison results tool" --domain product` — top
  structural match wasn't the Airline or Travel/Tourism Agency product
  profiles (those are vibrant, conversion-funnel, marketing-site
  patterns — wrong shape for a search-and-explain tool). The actual
  structural match was **Patent/IP Database**: "Search-First + Results
  Grid" landing pattern, "Data-Dense Dashboard" secondary style,
  **"Formal neutral + [type] chips + status badges (granted/pending/
  rejected)"** — structurally identical to this product's viability
  badge (`high/medium/low/unknown`) and connection-risk badge.
- `"formal trust neutral professional" --domain color` — the same
  Patent/IP Database color profile: slate/neutral base with badges
  layered on top, not a travel-brand palette.
- `"data dense dashboard neutral trust" --domain style` — confirms
  `data-dense-dashboard` style: minimal padding, grid layout, maximum
  data visibility, neutral base + data colors for status.
- `"clean readable data table professional" --domain typography` —
  **"Corporate Trust"** pairing (Lexend heading / Source Sans 3 body),
  tagged "Enterprise, government, healthcare, finance,
  accessibility-focused" — closer fit than a generic "modern sans."
- `"status badge check warning icon" --domain icons` — concrete Phosphor
  icon names for the exact states this UI needs (see Part B).
- `"badge chip label wraps" --domain ux` and `"status conveyed by color
  alone" --domain ux` — concrete Do/Don't rules applied directly into
  Part B's constraints (color is never the only signal; a chip either
  stays on one line or discloses full text, it never silently wraps).
- `"chip badge overflow nowrap responsive" --stack html-tailwind` and
  `"server component data fetching loading state" --stack nextjs` —
  exact Tailwind/Next.js implementation patterns, folded into Part B.

**Synthesis:** this product is closer to a trust-sensitive data tool
(patent search, financial dashboard) than to a travel-brand marketing
site — it has real money and an explicit promise never to fabricate
confidence. Style: Data-Dense Dashboard + Minimalism & Swiss Style,
**not** Aurora UI / Glassmorphism / vibrant destination colors (those
were the tool's own Travel/Tourism Agency match, and are the wrong fit
here). This also matches `docs/UI.md`'s own instruction — "a travel
command center, not an IRCTC clone" — with real data behind it instead
of just asserting it.

**Anti-patterns, stated so a design pass can't drift into them:**
- No "AI purple/pink gradient," no glassmorphism/neumorphism — decorative
  depth fights the actual job, which is fast comparative scanning of
  fare/time/risk across journeys.
- No fake urgency copy ("only 2 seats left!") — hard rule in `docs/UI.md`.
- No emoji-as-icon — the current `✓`/`⚠`/`✕` glyphs in `WhyThisRoute.tsx`
  and `ExpansionBanner.tsx` become real Phosphor icons (see Part B).
- No color-alone meaning — every badge pairs an icon + text label with
  its color, per the `ux-guidelines.csv` "Color Only" rule (severity:
  High).

**Information hierarchy:** on the results list, fare / duration /
transfer count / booking-viability badge / connection-risk badge must
be scannable in under 2 seconds per card. "Why this route" is
deliberately *not* on that screen (per `docs/UI.md`) — it's
detail-on-demand on the journey page, and must never be collapsed
there; it's this product's main trust-building element versus
ixigo/ConfirmTkt's single opaque percentage.

**Concrete tokens from the real query output** (used in Part A):
- Colors: Primary `#475569`, Secondary `#64748B`, Accent `#A16207`,
  Background `#F8FAFC`, Foreground `#1E293B`, Card `#FFFFFF`, Muted
  `#EAEFF3`, Border `#E2E8F0`, Destructive `#DC2626`
- Typography: Lexend (headings) / Source Sans 3 (body) — "Corporate
  Trust" pairing
- Icons (Phosphor): `CheckCircle` (success/verified), `Warning`
  (caution), `Check` (positive checklist item), `WarningCircle`
  (info/notice)

## PART A — Stitch design brief

**Paste this into stitch.withgoogle.com directly** (not Antigravity —
Antigravity's Stitch MCP connector only *fetches* an existing Stitch
project, it doesn't generate one; Part B fails until this project
exists). "Web" project type, name the project `journey-intelligence-v1`
exactly (Part B fetches it by this name).

```
Design a 3-screen web app called "Journey Intelligence" — an Indian
multi-modal train journey planner. Positioning: a "travel command
center," not an IRCTC clone or a generic OTA. It searches and explains
journeys; it never books anything, so there is no "Book now" button
anywhere.

Style direction: Data-Dense Dashboard blended with Minimalism & Swiss
Style — closer to a trustworthy financial/analytics dashboard (think
patent search or compliance tooling) than a flashy consumer travel
app. Generous spacing, strong type hierarchy, badges/labels instead of
raw percentages wherever a judgment is being communicated (e.g. "High"
not "87%"). Minimal padding on data-heavy areas, grid-based layout,
maximum information density without feeling cramped.

Color palette (slate/neutral base with status colors layered on top,
not a travel-brand palette): primary #475569, secondary #64748B,
accent #A16207, background #F8FAFC, card #FFFFFF, foreground #1E293B,
muted #EAEFF3, border #E2E8F0, destructive/error #DC2626. Status
colors for badges: green for positive/high-confidence, amber/yellow
for caution, red for risk/broken, neutral grey for "unknown" (a
common, expected, non-error state — never assign it a color that
implies confidence that doesn't exist).

Typography: Lexend for headings, Source Sans 3 for body text — the
"Corporate Trust" pairing: accessible, professional, high-legibility.

Iconography: Phosphor icon set, outline weight. No emoji as icons
anywhere. No stock-photo travel imagery — this is a tool, not an ad.
No fake urgency language anywhere ("only 2 seats left" style copy is
explicitly forbidden).

Screen 1 — Search (single form, no wizard/steps):
- Origin and destination fields, each with an autocomplete dropdown
  showing station name, code, and city
- A date RANGE (earliest date, latest date) — two date pickers, not one
- Optional budget max input (₹)
- Class selection as a multi-select chip/pill group: SL, 3A, 2A, 1A, CC
  — chips must stay on one line each (nowrap), never wrap mid-label
- Max transfers as a 3-option segmented control: 0 / 1 / 2
- Passenger count number input
- One submit button; while loading, show exactly one calm status line
  below the button (e.g. "Searching across your date range for viable
  journeys…") — never a fake multi-step progress bar, since the search
  is a single synchronous call, not a multi-stage pipeline

Screen 2 — Results list:
- Header showing the echoed query in plain language (route, date
  range, budget)
- Below the header, an optional dismissible info banner (amber/neutral
  tone, not alarming) suggesting nearby alternate stations when the
  exact search came back thin — must look clearly secondary/optional,
  never blended into the main list
- A vertical list of journey cards. Each card:
  - route as station codes joined by arrows (e.g. "BRC → NDLS → MFP")
  - total fare (large, prominent) and total duration + transfer count
    (secondary line)
  - a "booking viability" badge with exactly 4 states: High, Medium,
    Low, Unknown (neutral grey) — each badge pairs an icon AND a text
    label with its color, never color alone
  - a separate "connection risk" badge (green/yellow/red) reflecting
    the worst transfer in that journey — visually distinct from the
    viability badge, they answer different questions
  - the whole card is a link to the detail screen
- An empty state (genuinely no results, not an error): calm
  reassuring copy, one suggestion to loosen a constraint, button back
  to search with values preserved

Screen 3 — Journey detail:
- Back link to results
- Full leg-by-leg itinerary: train name/number, class, from/to station
  and time, fare — presented as a timeline/vertical stepper, not a
  table
- Per-transfer: buffer time, the same connection-risk badge, one-line
  plain-language reason (e.g. "1h05m at NDLS — moderate platform
  distance")
- A prominent "Why this route" section: a checklist of positive
  reasons (checkmark icons) rendered as its own clearly-labeled block —
  this is the single most important trust element on the page, never
  collapse it into a summary or hide it behind a toggle
- A separate "Cautions" list (warning icons) directly below or beside
  it, visually distinct (not the same color as the positive list)
- No booking CTA of any kind

All 3 screens: must work responsively from 375px through 768px, 1024px,
and 1440px without horizontal scroll or clipped text. Meaning never
rests on color alone.
```

## PART B — Antigravity implementation prompt

Run after: Antigravity → Agent Manager (Cmd/Ctrl+E) → MCP Servers →
install "Stitch" → paste your Stitch API key → verify with "List my
Stitch projects" and confirm `journey-intelligence-v1` appears (i.e.
after Part A has actually been run in Stitch, not before).

```
Use the Stitch MCP to fetch the "journey-intelligence-v1" project.
Extract the color palette, typography, spacing scale, and component
styling into a DESIGN.md file at the root of this repo.

Then implement this design into the EXISTING codebase at apps/web — do
not scaffold a new app or change the framework. This is a Next.js 14
App Router + TypeScript + Tailwind project. Existing structure to
update in place:

  apps/web/app/page.tsx                        Search screen
  apps/web/app/results/[id]/page.tsx            Results list screen
  apps/web/app/results/[id]/[rank]/page.tsx     Journey detail screen
  apps/web/app/components/SearchForm.tsx
  apps/web/app/components/StationAutocomplete.tsx
  apps/web/app/components/JourneyCard.tsx
  apps/web/app/components/ViabilityBadge.tsx
  apps/web/app/components/ConnectionRiskBadge.tsx
  apps/web/app/components/WhyThisRoute.tsx
  apps/web/app/components/ExpansionBanner.tsx
  apps/web/app/lib/types.ts                     the real data shapes below

Bind to these EXACT TypeScript types — do not invent field names:

  interface JourneyLeg {
    trainNumber: string; trainName: string;
    fromStationCode: string; toStationCode: string;
    departure: string; arrival: string; durationMinutes: number;
    classCode: string; fareEstimate: number;
  }
  type ConnectionRisk = 'green' | 'yellow' | 'red';
  interface ConnectionBuffer {
    atStationCode: string; minutes: number; risk: ConnectionRisk; reason: string;
  }
  type BookingViability = 'high' | 'medium' | 'low' | 'unknown';
  interface Journey {
    legs: JourneyLeg[]; totalFareEstimate: number; totalDurationMinutes: number;
    transferCount: number; connectionBuffers: ConnectionBuffer[];
    departureTime: string; arrivalTime: string; journeyQualityScore: number;
    bookingViability: BookingViability;
    whyThisRoute: string[]; cautions: string[];
  }
  interface ExpandedStation { stationCode: string; extraTravelMinutes: number; }

Use the Phosphor icon library (@phosphor-icons/react) to replace the
current emoji glyphs (✓ ⚠ ✕) in WhyThisRoute.tsx and
ExpansionBanner.tsx:
  - CheckCircle (weight="regular") for "why this route" positive items
  - Warning (weight="regular") for cautions
  - WarningCircle (weight="regular") for the expansion banner's info
    tone
  - Check for compact inline confirmations
Give each icon an accessible role per its context: aria-hidden="true"
when it sits beside visible text that already says the same thing;
otherwise a text alternative.

Follow these UX rules from the ui-ux-pro-max skill's data (not generic
preference — these are the concrete Do/Don't pairs it returned):
  - Chip/badge labels: "flex flex-wrap gap-2" for the collection; each
    label "min-w-0 whitespace-nowrap truncate", dismiss icons
    "shrink-0". Never let a single label wrap to a second line inside
    a pill.
  - Color is never the only signal: every risk/viability badge pairs
    an icon AND a text label with its color.
  - For the results page's loading behavior, prefer Next.js's own
    app/results/[id]/loading.tsx route-loading convention over manual
    client-side loading state, per Next.js App Router guidance — but
    keep SearchForm's own inline one-line status text as-is, since
    that's a client-side form-submission wait, not a route transition.

Non-negotiable product constraints — do not "improve" these away
during the redesign, they are product requirements, not placeholder
styling:
- The Unknown viability state renders in a neutral/grey style that
  cannot be mistaken for a real signal.
- "Why this route" and "Cautions" on the detail page always render
  explicitly and separately — never merged into the summary score,
  never hidden behind a collapsed/expand toggle.
- No dark patterns, no fake urgency/scarcity copy anywhere.
- No booking CTA of any kind on any screen.
- Keep the app working from 375px to 1440px with no horizontal scroll.

Do NOT touch: apps/api/, packages/journey-engine/, infrastructure/.
This is a UI-layer redesign only — the search/ranking logic and API
contract are unchanged.

After implementing, open the app in the integrated browser and compare
each screen against the Stitch design. If you need to add a small
component library (e.g. class-variance-authority for badge variants)
that is fine, but do not introduce a full UI kit (e.g. shadcn/ui)
without flagging it first — the project's ARCHITECTURE.md currently
says plain Tailwind is enough for V1 and treats that as a decision to
revisit explicitly, not to silently override.
```
